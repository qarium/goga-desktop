## Структура и проверки

Приложение использует Electron, React и TypeScript.

- `src/main/` — основной процесс Electron, окна, preload, IPC и ограничения безопасности.
- `src/host/` — локальные проекты, рабочие копии, Goga, Git, настройки и состояние запусков.
- `src/renderer/` — интерфейс React, формы, выбор контекста и черновики.
- `src/shared/` — общие типы, схемы и области действия операций.
- `tests/` — тесты Vitest; `scripts/` — сборка, локальная подпись и проверочные сценарии.

Используйте lockfile и при необходимости `npm ci` в указанном основном репозитории, без создания отдельной рабочей копии. Основные команды:

```sh
npm test
npm run typecheck
npm run build
```

Они запускают Vitest, проверку TypeScript и сборку Vite с упаковкой основного процесса соответственно. Сборка не запускает приложение. `npm start`, `npm run dev`, `npm run package` и smoke/harness-сценарии не относятся к этим трём проверкам: сначала изучите их эффекты и получите необходимое разрешение. Не заявляйте об успешной проверке без фактического результата.

## Безопасность и границы изменений

- Без явного разрешения не запускайте настоящие конвейеры Goga, Docker, приложение или сценарии, способные изменить пользовательское окружение. Не меняйте настоящий HOME, пользовательские проекты, настройки, репозитории и учётные данные.
- Проверки выполняйте с временными каталогами, тестовыми репозиториями и подставными исполнителями. Не подменяйте ими пользовательские каталоги. Не используйте реальные секреты в фикстурах, логах или отчётах.
- Не отключайте Gatekeeper и другие защитные механизмы. Ad-hoc-подпись не равна Developer ID или нотариализации; не используйте личные сертификаты автоматически.
- Не выполняйте разрушительные Git-операции и не меняйте удалённые репозитории без отдельного разрешения.

## Изоляция контекстов

Владение данными задаётся проектом, годом, топиком, веткой и выданным хостом `contextId`; `revision` отдельно определяет актуальность запросов. Черновики дополнительно разделяются по виду запуска. Не объединяйте контексты по одному имени топика, не переносите черновики, результаты и поздние ответы между владельцами. Недоступная рабочая копия не должна незаметно заменяться основной папкой проекта.

Проверка путей и полномочий остаётся на стороне хоста: выбор в интерфейсе не даёт права на запись. Сохраняйте проверки владельца, ревизии, токенов подтверждения и областей IPC. Синхронизация импортирует коммиты в служебные ссылки; применение в текущую базовую ветку требует отдельного предварительного просмотра и подтверждения. Ни синхронизация, ни применение не означают публикацию на сервер.

## Контракт разработки и выпуска

Следующие правила — контракт, а не утверждение о наличии или успешном выполнении CI.

- Публикация выполняется из `main` основного репозитория, продолжая существующую историю `origin/main`. Добавляйте в коммит только проверенные файлы задачи; не переносите посторонние изменения и приватную локальную историю. Не заменяйте `.git` и не переписывайте опубликованную историю без отдельного разрешения.
- Каталоги с именем `docs` в любом регистре и на любой глубине никогда не публикуются. Также исключайте локальные состояния, секреты, зависимости и результаты сборки. `.gitignore` не удаляет уже отслеживаемые файлы: проверяйте состав публикуемого снимка и всей публикуемой истории отдельно.
- Версия релиза выводится только из строго проверенного тега `vX.Y.Z` или `vX.Y.Z-alpha.N`, `vX.Y.Z-beta.N`, `vX.Y.Z-rc.N`. Все числовые части — неотрицательные целые без ведущих нулей, кроме самого `0`; дополнительные суффиксы и метаданные не допускаются. В артефакте используется версия без начального `v`.
- Не делайте ручной version bump ради релиза. Если версия подставляется при сборке, это происходит только во временном снимке; CI не коммитит и не отправляет изменения версии обратно в репозиторий.
- Первый выбранный тег — `v0.0.0`; наличие тега ещё не означает успешный выпуск. Локальная версия `0.1.51` не является доказательством выпуска. macOS arm64 и x64 — планируемые цели, а не подтверждённая совместимость.
- Текущая упаковка настроена на ad-hoc-подпись без Developer ID и нотариализации. Сборка, подпись, установка и запуск — разные проверки; не выдавайте одну за остальные и не обещайте публикацию без проверенных артефактов.

### Реализованные команды CI и выпуска

- `npm run test:release` — автономные тесты правил CI, упаковки, DMG-проверок и publisher; все сетевые вызовы publisher заменены подставным транспортом, публикация не выполняется.
- Автоматический CI проверяет push в `main` и pull request только на macOS arm64: полный Vitest, контракты CI/выпуска, TypeScript и сборку. Полный x64-набор доступен только через `workflow_dispatch` в `intel-tests.yml` и не блокирует релиз. Домены ARM заданы в `scripts/ci-test-domains.json`: Git workspace, конфликты, безопасность, топики/клоны, терминал, запуски, документы/настройки и оболочка. UI-тесты относятся к своему домену. При добавлении/удалении тестового файла обновляйте владельца: пропущенные, устаревшие и дублирующиеся записи завершают CI ошибкой. Подгруппы балансируются отдельными ARM-весами, не Intel-оценками.
- Полный ARM Vitest использует `--maxWorkers=3 --testTimeout=15000`, дополнительная Git-совместимость — также три, ручной Intel — один worker. На одинаковых 163 Git-сценариях локальный запуск с тремя изолированными workers занял 314,44 с вместо 669,08 с; это не замер всего CI. Изменение параллельности требует замера и проверки изоляции. `verbose` показывает завершение отдельных тестов; JSON-отчёт перечисляет точные имена пропусков. `GOGA_TOPIC_READONLY_CLI=/nonexistent/disabled` сохраняет существующие opt-in исключения настоящего Goga CLI; новых пропусков нет. Цель — не более 15 минут всего автоматического CI, включая подготовку; лимит 15 минут отдельного job сам по себе не доказывает достижение цели. Сборка идёт параллельно оставшимся тестам; итоговый gate требует успешности всех доменов, совместимости Git и сборки.
- `RELEASE_TAG=vX.Y.Z npm run release:version` подставляет проверенную версию только в временном checkout. `node scripts/release-version.mjs --check` только проверяет тег. Локальная версия не означает релиз.
- `npm run package:release -- --arm64` (либо `--x64`) упаковывает уже собранное приложение, без публикации и автопоиска сертификатов. Сначала необходим `npm run build`. Артефакт: `Goga-Desktop-VERSION-ARCH.dmg`; ad-hoc, без Developer ID и нотариализации.
- Release workflow публикует только по push тега `v*`; ручной `workflow_dispatch` разрешён только из `main`, использует строгую тестовую версию и никогда не запускает publisher/создание тега или релиза. Оба режима проверяют строгий тег, принадлежность коммита истории `origin/main` и успешный полный ARM CI именно этого коммита. Полный Vitest, автономные тесты правил выпуска и TypeScript в релизе повторно не запускаются: они остаются обязательными в CI точного коммита. На обеих архитектурах после сборки/упаковки выполняется только короткий smoke готового DMG. Ручной Intel CI не заменяет успешный ARM CI. Обе архитектуры упаковываются и проверяются нативно: arm64 на `macos-15`, x64 на `macos-15-intel`; проверяется архитектура системы, Node и executable из DMG. Cross-build не считается доказательством поддержки.
- `RELEASE_TAG=vX.Y.Z node scripts/verify-dmg.mjs FILE arm64|x64 [--ui]` **монтирует DMG и запускает его executable** в режиме Node в изолированном временном HOME; проверяет read-only mount, Applications link, ad-hoc codesign, Mach-O, ASAR/Info.plist/renderer version и снимает mount. `--ui` дополнительно запускает именно executable из смонтированного DMG через штатный packaged main. Внешний Node 24 контроллер включает ephemeral CDP только на loopback для этого тестового процесса, не меняя devTools/sandbox продукта; используются настоящий preload/Host и IPC. В одноразовых HOME/профиле проверяются версия/готовность, сохранение настройки, один Git-коммит в новом локальном репозитории без remote/хуков/подписи, ввод/вывод настоящей PTY, безопасное закрытие сессии и штатный выход приложения. Goga/Docker и пользовательские проекты/сессии не используются. Это не Finder-запуск, установка, Gatekeeper-проверка или доказательство работы на чистом Mac. Не запускайте эти команды без соответствующего разрешения.
- Publisher имеет запись только в отдельном job после успеха обеих сборок. Публикуются ровно два DMG и `SHA256SUMS`; сначала создаётся draft, проверяются серверные имена/размеры/SHA-256 и состояние draft, затем он публикуется. Любой существующий релиз, включая draft, блокирует повторный запуск; частичный draft требует ручного восстановления, автоматического удаления/перезаписи нет. Разрешён только `qarium/goga-desktop`; тег должен уже существовать и указывать на ожидаемый commit. Publisher и workflow не создают и не отправляют теги или version-back commits.
- Все Actions закреплены полными SHA. CI/build jobs имеют только `contents: read`, не получают секреты и не сохраняют Git credentials. Ни CI, ни release workflow не запускает настоящие конвейеры Goga/Docker. Наличие workflow ещё не доказывает успешный выпуск на GitHub или поддержку обеих архитектур.

### Медленные Git-интеграционные тесты на Intel

`GOGA_TEST_PROFILE=slow-git` применяется к полному Vitest в ручном Intel workflow. Он увеличивает конечные бюджеты явно отмеченных измеренных Git-интеграционных сценариев через `tests/helpers/git-integration.ts`; остальные тесты, продуктовые дедлайны, проверки владельцев и блокировок не меняются. `slow-git` умножает эти бюджеты на три; `default` не применяет множитель. Отдельный конечный дедлайн теста реального CloneManager поднят с 2,5 до 10 секунд (30 секунд в `slow-git`), чтобы отличать медленные Git-команды от взаимной блокировки; сам resolver и проверки результата сохранены. Неизвестное имя профиля должно завершать проверку ошибкой. Пропусков, автоматических повторов упавших тестов и допуска публикации при ошибках нет.

Автоматические ARM jobs ограничены 15 минутами, ручные Intel jobs — 60 минутами. Исторический Intel-прогон занял 41 минуту; он не входит в автоматический CI. Успех локального прогона на arm64 не доказывает успех x64; нужен новый нативный CI. Существующий тег не перемещается ради исправления.

### Независимые группы тестов CI

Полный ARM-набор разделён по восьми доменам с подгруппами для тяжёлых зон; ручной Intel — на восемь полных подгрупп. Веса влияют только на распределение, не на покрытие. Проверка Git 2.45.2 сохраняет все шесть файлов в одном задании с тремя изолированными workers. Кешируется проверенная по SHA256 сборка Git с ключом платформы/архитектуры/toolchain и скрипта сборки, а также npm-download cache; результаты тестов не кешируются.

### Штатный Git и граница Host/API

- Host направляет commit/discard/conflict-save в `NativeGitWorkspaceActions`, `NativeGitDiscardActions`, `NativeGitConflictActions`; ветки, merge, rebase, cherry-pick/revert и Goga handoff используют native-журнал. Общие `Git*Actions` содержат только admission/preview и не имеют старого исполнителя или fallback по версии Git.
- Перед записью сохраняются проверки владельца, ревизии, одноразового подтверждения, рабочего дерева/индекса и неизменности остановленной операции. Native-журнал и защитный снимок не заменяются флагом успеха команды. Неизвестный результат сохраняет материалы и блокирует автоматический повтор.
- При работе с существующим клоном служебная блокировка не создаёт и не исправляет его каталоги/права. Потеря владельца не переводит запись в основную папку проекта. Ошибки действия и освобождения контекста проходят очистку секретов, включая аварийный выход после записи.
- UI подтверждает завершение остановленной Git-операции только по наблюдаемому native-результату правильного scope/action, завершённому процессу, проверенной сохранности несвязанных данных и завершённой очистке восстановления; одного `status: success` недостаточно. Закрытие окна не отменяет выполняющуюся запись.
- При миграции тестов переносите пользовательские инварианты на native spawn/exit/readback/recovery boundaries. Не сохраняйте искусственные HEAD/index pins или ручную сериализацию Git ради старого fault injection; не удаляйте проверку без подтверждённой замены. Полный прогон текущего плана — только N8.

### Дополнительная совместимость Git в CI

- Помимо полного ARM-набора CI содержит обязательные группы `git-compatibility` на macOS: Git 2.45.2 собирается из архива с закреплённой SHA-256 в `$RUNNER_TEMP`, системный Git не меняется. `scripts/test-git-compatibility.mjs` сначала проверяет точную версию, затем выполняет шесть целевых файлов целиком; это не замена полного покрытия.
- `complete` требует успеха всех доменных подгрупп, групп compatibility и независимого `check`. Release gate по-прежнему требует успешный CI точного SHA.
- Native merge/sequence/branch/handoff завершают очистку recovery в общей внешней границе `withNativeGitCompletion`. Вложенный handoff не финализирует журнал раньше вызывающего контекста; returned uncertainty, ошибка внешнего контекста или неизвестная очистка сохраняют fence и не считаются success. Выбранные commit/discard/conflict writers сохраняют свои явные deferred cleanup guards.

### Изоляция длинных Git-проверок после native migration

CI N8 подтвердил, что длинные составные Git-сценарии превышают прежние 15 секунд (на arm64), а на Intel даже более короткие циклы требуют профиля `slow-git`. Конечные бюджеты задаются явно в затронутых тестах через `gitIntegrationBudget`; общий `testTimeout=15000`, отдельные продуктовые дедлайны и assertions не меняются. Полные lifecycle-сценарии с подготовкой, несколькими остановками, сохранением и завершением имеют отдельные конечные бюджеты. Это не разрешение увеличивать timeout без измерений.

`installGitFixtureScope` отслеживает setup и полное тело каждого затронутого сценария: незавершённая работа должна завершиться до удаления временных репозиториев и восстановления spies. Cleanup ограничен, незавершённый scope блокирует следующий тест. Составные Host lifecycle-проверки используют независимые репозитории и реально воспроизводят предыдущие шаги, вместо передачи изменяемой beforeAll-фикстуры следующему тесту после timeout. Автоматический maintenance отключён только у синтетических setup-команд; продуктовые политики не ослаблены.

Повторный CI показал неодинаковое замедление файлов (до медианы 9×), поэтому крупнейший `git-rebase-conflict-save` разделён на четыре самостоятельно обнаруживаемых файла с общей только библиотекой фикстур: у каждого файла/теста свой scope и репозиторий. Тела сценариев и assertions при переносе сохраняются. Веса не заменяют тайм-ауты; полный охват проверяется независимо от их значений.

В интеграционных Host writer-фикстурах (apply, commit, discard, merge/sequence и сохранение конфликтов) используется конечный штатный лимит NodeRunner (120 с) вместо искусственного лимита 10 с: подготовленная ref-транзакция включает вложенные проверки владельца/снимка. Отдельные тесты транспортных тайм-аутов сохраняют свои короткие deadlines; продуктовый лимит не меняется. Замедленный локальный probe воспроизвёл отказ update-ref на 10 с и успех того же сценария с production default.

UI-тесты ожидают снятия `aria-busy` перед дорогим поиском по доступному имени и `disabled=false` перед нажатием. Это ожидание готовности, а не повтор клика или увеличение UI-тайм-аута; проверка видимости и доступности самого элемента остаётся.

### Оптимизация тестовых данных и ограниченный release smoke

`RepositorySeeds` хранит в памяти worker только неизменяемые синтетические репозитории до начала Git-операции. Каждый сценарий получает собственные файлы, refs и индекс без hard links; состояние конфликтов и продуктовые проверки каждый раз выполняются заново. Не сохраняйте там результаты проверок, контрольные файлы активных операций, рабочие копии пользователя или Host ownership. Семена разделены параметрами сценария и PATH выбранного Git.

DMG smoke имеет общий бюджет работы 160 секунд и отдельные 20 секунд на снятие mount; workflow ограничивает шаг четырьмя минутами с запасом на обвязку. Неполная проверка блокирует публикацию. Это не полный регрессионный Intel-набор и не обещание времени упаковки. Подпись, версия, архитектура, нативный addon и изолированный packaged UI остаются обязательными.

Сборка явно выполняет `node_modules/electron/install.js` из установленной lockfile-зависимости в изолированном build HOME перед проверкой Mach-O и пересборкой node-pty. Electron 44 загружает executable лениво; наличие npm-пакета после чистого `npm ci` не означает наличие binary. Не заменяйте этот шаг запуском приложения или общим разрешением install-скриптов всех зависимостей.

На доступных пяти macOS runners лишнее дробление увеличивает очередь: ARM имеет одиннадцать подгрупп в восьми доменах (конфликты — четыре, остальные — по одной), плюс отдельные compatibility и check. Полный охват проверяется против обнаружения Vitest; число jobs не доказывает достижение целевого времени.


CI 40692428549 выявил не только очередь, но и timeout длинных сценариев конфликтов: локальные веса недооценивали их неодинаковое замедление на runner. Веса конфликтов обновлены по этим удалённым замерам; неполные файлы оценены по локальному полному прогону и наблюдавшемуся коэффициенту 2,7. Это только планирование, не отбор тестов. Domain sequencer запускает файлы по убыванию стоимости; локальные/ручные full-run вне доменов сохраняют обычную сортировку.

В первую очередь допускаются четыре подгруппы конфликтов, топики и compatibility; GitHub ограничивает одновременно работающие macOS runners. После завершения compatibility запускаются workspace и check; после check — остальные пять коротких доменов. У зависимых заданий `if: !cancelled()` сохраняет запуск при обычном падении предшественника; отказ любого задания всё равно блокирует итоговый gate. Приоритетная Git-волна использует существующий конечный профиль `slow-git` для измеренных длинных integration-сценариев, а не меняет лимиты операций приложения или assertions. Общий timeout каждого задания по-прежнему 15 минут. Факт прохождения и полного времени нового CI нужно подтвердить удалённым запуском, не моделью очереди.


Для ARM (и lower-Git compatibility) замер на одинаковых 154 сценариях показал 227,80 с с четырьмя изолированными workers против 280,82 с с тремя; имена/результаты сверяются с исходным отчётом. Полный Intel остаётся с одним worker. Workspace и compatibility также используют конечный integration-профиль `slow-git`: он масштабирует только тестовую обвязку Git, не продуктовые сроки и не generic unit/UI timeout 15 с.

Последовательный файл `git-rebase-read-admission` на runner занимал 655,52 с и стал нижней границей времени, независимо от числа свободных workers. Его 50 сценариев теперь разделены на три независимо обнаруживаемых файла (21/15/14), общая библиотека создаёт новый scope и репозиторий для каждого теста; тела и assertions сохраняются. При переносах проверяйте тождественность сценариев и exact-once discovery, не заменяйте полный охват списком разрешённых файлов.

`RunRecoveryManager.launch()` возвращает admission-ready до атомарной замены lease при переходе started. Тесту операций над уже работающим payload требуется сначала дождаться собственного PID-marker. Однократная проверка защищённого lease во время его атомарной замены вправе fail closed; не снимайте проверки link count/владельца и не объявляйте такой read доказательством остановки процесса.


### Блокировка выпуска: подтверждённые ограничения runners

Четыре workers показали локальное ускорение, но на GitHub привели к перегрузке: три группы конфликтов выполнили все1056assertedcases, но не уложились в15мин job. Рабочая ARM-конфигурация возвращена к трём workers (последний такой удалённый прогон выполнил эти сценарии в пределах15мин); конфликты разделены на четыре меньших подгруппы с тем же покрытием. Intel остаётся с одним worker. Общий15мин wall-clock, включая очередь GitHub, не подтверждён и не гарантируется лимитом отдельного job.

Ручной `ci-diagnostics.yml` сравнивает1/2/3workers на четырёх одинаковых тяжёлых сценариях, сохраняет JSON и ресурсы runner. Он не запускается при push/PR, не заменяет обязательный CI и не допускает релиз. Во время финального полного CI не запускайте диагностику, конкурирующую за те же macOS slots.

Два selected-commit сценария с~700Git-командами отнесены к существующему конечному integration-профилю: default15с, slow-git45с. Все assertions, проверки recovery/flags/CRLF/binary и продуктовые сроки сохранены. Терминальная PTY-фикстура сначала разрешает фактический sys.executable ApplePython отдельным конечным preflight, затем запускает интерпретатор напрямую; холодная инициализация Xcode не должна съедать прежний3с shell-state deadline. Прежний10с test budget не увеличен.

### Короткий smoke упакованного приложения

Релизные native jobs ограничены 15 минутами работы каждый; установка, сборка и упаковка имеют отдельные конечные бюджеты и `phases.jsonl`. Smoke сохраняет общий бюджет 160 секунд и отдельные 20 секунд cleanup (внешний шаг — четыре минуты). Это ограничения, не доказательство достижения целевого времени или выделения GitHub runner. Проверка Intel требует Intel runner, результат ARM её не заменяет.

Кешируются только загрузки Electron, headers внутри изолированного build HOME и инструменты electron-builder; ключ включает архитектуру, lockfile и toolchain. Нативные модули каждый раз пересобираются и проверяются по версии, архитектуре и хешам. Итоги smoke, app state, node_modules и готовые артефакты не кешируются. Не пробрасывайте пользовательские Electron/Node injection flags в installer или smoke child.

`GOGA_RELEASE_REPORT_DIR` задаёт отдельный каталог ограниченных JSON/log/PNG-отчётов; workflow выгружает только `work/release-report/`, в том числе при отказе. HOME, временный Git и весь профиль в диагностику не входят. Отсутствующий/неполный receipt, fatal/protocol ошибка, нештатный выход, неподтверждённое завершение тестовых процессов или отказ unmount не считаются успешным smoke. Отказ удаления уже отключённой временной папки сообщается отдельно с сохранением пути; он не является доказательством работающего процесса и не скрывается. Публикация по-прежнему требует зелёного полного CI точного SHA и успеха обеих native сборок; при ошибке проверки не пропускаются и не повторяются автоматически.

В полном CI `e36d015` конфликтная группа 4/4 достигла 15 минут до завершения (пройденные сценарии без assertion failures); она включала Host/rebase файл с 720,433 с суммарного времени тестов. Набор перераспределён на пять групп с теми же тремя workers и прежним 15-минутным лимитом. Exact-once discovery проверяет полный набор; это не добавляет повторный Vitest в release и не гарантирует очередь GitHub.

На runner прогона `6e7319b` группа 3/5 достигла 15 минут без ошибок утверждений; Host sequence занял 833,868 с против старого веса 480, write-races — 697,756 с против 346. Конфликты распределены на восемь групп; ARM-веса повышены по фактическим журналам, а незавершённый lifecycle не принимается за полный замер. Тела и владельцы тестов, три workers и 15-минутный лимит прежние; exact-once проверяет все файлы. Эти оценки планирования не гарантируют время runner или очереди.

Сценарий native commit «expires tickets and denies replay» выполняет две полные подготовки и один коммит настоящим Git; на ARM runner он достиг 15,161 с. Только этот сценарий использует `gitIntegrationBudget(15000)`: local/default остаётся 15 с, существующий slow-git — 45 с. Истечение проверяется внедрёнными часами, а не реальной задержкой; TTL, защита повторного исполнения, assertions и 15-минутный job limit не меняются.
